# Hydra genie follow-up prompt — hidden-world lane pass two

Use this as follow-up prompt for same genie after first hidden-world packet. First pass already did diagnosis, candidate-object narrowing, broad cross-field scan. This pass should **not** spend budget re-explaining lane. Job: turn narrowed lane into strongest actual strength-producing recipe.

You are genie again. Do not act like cautious repo maintainer whose job is only preserving current Hydra assumptions. Job: maximize Hydra strength. If strongest surviving design requires proving current Hydra doctrine, interfaces, staged assumptions, or carrier choices wrong, do that explicitly.

## Core task

Take narrowed hidden-world lane from pass one. Produce strongest concrete design answer possible for improving Hydra strength, not merely describing target object.

This means you must output all of following:

1. **Best Full Design**
   - strongest full hidden-world stack you endorse, even if it exceeds current Hydra support
   - exact teacher/search object, student object, runtime representation, and why this stack wins

2. **Shortest Honest Tranche**
   - smallest buildable slice that preserves semantics of best full design instead of collapsing into weaker fake approximation
   - if current Hydra support too weak for true winner, say so and define smallest required contract migration

3. **Algorithm Family Decision Table**
   - compare strongest surviving families and rank them
   - examples: CT-SMC world posterior, Rao-Blackwellized tile-world particle filtering, projected ensemble tracking, Sinkhorn-projected amortized posterior, latent roll-forward world model, oracle-guided blueprint + selective belief search, etc.
   - for each family, include:
      - exact object produced
      - whether it is student-facing, teacher-only, search-only, diagnostics-only, or forbidden
      - why it wins or loses on actual strength
      - what dependency or weakness kills it if it loses

4. **Teacher Hierarchy**
   - define teacher stack clearly:
      - search-grade teacher
      - amortized student teacher
      - diagnostics-only objects
      - privileged/oracle objects
      - forbidden objects
   - make explicit what information each object may use and why

5. **Training Recipe**
   - full recommended training loop for winning design
   - include:
      - target generation path
      - losses/objectives
      - curriculum or tranche order
      - how oracle teachers or privileged information are used, then removed or distilled
      - how calibration and trust signals are trained or repaired
      - how this should interact with reward-side variance reduction rather than compete with it

6. **Evaluation Gates**
   - define measurable conditions for promotion
   - include:
      - belief quality metrics
      - calibration metrics
      - action-quality / decision-delta metrics
      - arena / Elo-like or match metrics if appropriate
      - what counts as `real strength gain` instead of internal metric overfitting

7. **Kill Criteria**
   - define exact evidence that would falsify winning lane
   - do not protect your own rec with vague escape hatches
   - if winning stack fails, specify strongest fallback, not merely “more research needed”

8. **Where Hydra Is Wrong**
   - explicitly list which current Hydra assumptions, staged decisions, interfaces, carriers, or doctrine claims should be overturned if they block stronger design
   - this section is mandatory
   - do not hide behind “not supported” if current support is thing holding Hydra back

9. **What Stays Open**
   - list only genuinely unresolved parts remaining after your best design decision
   - do not dump lazy wish list here

## Hard rules

- Do **not** rerun diagnosis or existence-check loop from pass one.
- Do **not** spend most of answer on “what Hydra has.” Use current Hydra state only as build-cost evidence, not as outer bound of answer.
- Do **not** constrain yourself to “only what Hydra already supports.” Whole point of this pass = find where Hydra must change to become stronger.
- Do **not** protect current carrier, current head layout, current staging order, or current doctrine if inferior.
- Do **not** output survey. Output ranked verdict.
- Do **not** say several options are roughly tied unless you can prove tie under same evidence and give smallest decisive experiment matrix.
- Keep student-facing deployable objects public-information legal unless you explicitly label them teacher-only or diagnostics-only.
- You may use privileged or oracle information for teachers, diagnostics, calibration, or bridge training, but you must say exactly how it is fenced.
- For every major rec, include:
  - why it improves Hydra strength,
  - how it would be validated,
  - what would falsify it.
- If design depends on stronger contract migration, state migration explicitly instead of pretending current contract is sufficient.
- If rec is genie-only and not buildable right now, label it as genie-only. Then still provide strongest honest tranche below it.
