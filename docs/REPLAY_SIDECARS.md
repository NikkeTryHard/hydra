# Hydra Replay Sidecars

Operational guide to Hydra's replay-side supervision artifacts: ExIt sidecars and DeltaQ sidecars.

This document explains what the sidecar builders emit, how training consumes those artifacts, and what provenance checks must match before Hydra will hydrate replay-time labels from them. For the high-level training entrypoint, read [`docs/TRAINING_WORKFLOWS.md`](TRAINING_WORKFLOWS.md).

## What a replay sidecar is

A replay sidecar is an offline JSONL artifact keyed against replay decisions. It carries supervision that Hydra does not want to recompute inline during normal replay loading.

Hydra currently supports two replay-sidecar lanes:

- ExIt sidecars
- DeltaQ sidecars

Both are generated from:

- a replay input (`.json` or `.json.gz`)
- a checkpoint identity
- a source version

Both are then optionally joined during replay loading if the replay decision keys and provenance checks match.

## Shared CLI shape

Both sidecar builders use the same shared CLI skeleton:

```bash
build_replay_*_sidecar \
  --input <replay.json|replay.json.gz> \
  --checkpoint <model_base> \
  --output <sidecar.jsonl> \
  --source-version <u32> \
  [--min-visits <u32>] \
  [--hard-state-threshold <f32>] \
  [--max-kl <f32>]
```

Those shared flags live in `crates/hydra-train/src/bin/common/replay_sidecar_common.rs`.

### Shared flag meaning

| Flag | Meaning |
|---|---|
| `--input` | Replay source file to analyze |
| `--checkpoint` | Model base/checkpoint identity used to generate labels |
| `--output` | JSONL sidecar output path |
| `--source-version` | Version tag stored into the sidecar and required again at join time |
| `--min-visits` | ExitConfig visit budget threshold override |
| `--hard-state-threshold` | ExitConfig hard-state threshold override |
| `--max-kl` | ExitConfig KL safety-valve override |

## ExIt sidecars

ExIt sidecars are generated by:

- `crates/hydra-train/src/bin/build_replay_exit_sidecar.rs`

The output record type is:

- `ReplayExitRecordV1`

Important fields in each record include:

- replay decision key
- selected action
- legal-mask digest
- `source_net_hash`
- `source_version`
- root visit count
- supported action count / coverage
- target array and mask array

Conceptually, ExIt sidecars capture replay-indexed search-derived labels for root decisions so training can hydrate ExIt supervision without re-running the full live search pass during every replay load.

## DeltaQ sidecars

DeltaQ sidecars are generated by:

- `crates/hydra-train/src/bin/build_replay_delta_q_sidecar.rs`

The output record type is:

- `ReplayDeltaQRecordV1`

Important differences from ExIt sidecars:

- DeltaQ currently requires `source_version == 1`
- the validation contract is stricter about legal actions and target/mask semantics
- the lane is still not default-on even though the tooling is implemented

Conceptually, DeltaQ sidecars capture replay-indexed child-minus-root value deltas for supported discard actions.

## What `source_version` and `source_net_hash` do

Hydra uses both `source_version` and `source_net_hash` as part of provenance identity when replay loading attempts to hydrate labels from sidecars.

- `source_net_hash` is derived from checkpoint identity
- `source_version` is an explicit operator-supplied version tag

Hydra will refuse to hydrate a sidecar label when these do not match the replay loader's expected provenance.

This is deliberate. Sidecars are not generic labels; they are contract-bound artifacts tied to a replay identity, checkpoint lineage, and versioned semantics.

## How replay loading consumes sidecars

Replay loading uses sidecars only when all relevant checks pass.

That includes:

- replay identity / decision key match
- action match
- semantic/provenance version match
- legal-mask digest match
- `source_net_hash` match
- `source_version` match

### Identity matching for loose files versus archives

The source-identity part of that contract is intentionally not the same for all replay shapes.

- Loose replay loading joins sidecars by the replay file name Hydra loads, not by an absolute host path.
- Archive-backed replay loading joins sidecars by the explicit archive-entry identity string, for example `replays.tar.zst/path/inside/game.json`.
- That means a sidecar record keyed only to `game.json` will match a loose replay load of `game.json`, but it will not match an archive entry whose identity is `replays.tar.zst/path/inside/game.json`.

This distinction matters because Hydra treats archive entries as first-class replay identities rather than as anonymous extracted files. It avoids accidental collisions between two different archive entries that happen to share the same base file name.

Operationally:

- if you generate or inspect sidecars for loose replay files, expect file-name identity semantics
- if you generate or inspect sidecars for archive-backed replay corpora, expect full archive-entry identity semantics
- if a sidecar looks structurally valid but hydration does not happen, mismatched identity shape is one of the first things to check

For ExIt, the lookup returns target/mask arrays when the sidecar contract matches.

For DeltaQ, Hydra additionally validates that:

- the target/mask arrays have the expected action-space shape
- masked actions are legal discard actions
- non-masked entries do not carry stray target mass

This is why replay sidecars are safe to use as optional replay supervision rather than blind annotation files.

## How to make training consume them

Training consumes replay sidecars through config fields:

- `exit_sidecar_path`
- `delta_q_sidecar_path`

When these are configured, replay loading attempts sidecar hydration during replay decision preparation and target construction.

Use this when:

- you want replay-time ExIt or DeltaQ supervision without recomputing labels on the fly
- you need reproducible sidecar provenance tied to a specific checkpoint/version pair

## Example workflow

### Generate an ExIt sidecar

```bash
cargo run -p hydra-train --bin build_replay_exit_sidecar -- \
  --input /data/game.json.gz \
  --checkpoint /models/model_base \
  --output /output/game.exit.jsonl \
  --source-version 7 \
  --min-visits 128 \
  --hard-state-threshold 0.35 \
  --max-kl 1.5
```

### Generate a DeltaQ sidecar

```bash
cargo run -p hydra-train --bin build_replay_delta_q_sidecar -- \
  --input /data/game.json.gz \
  --checkpoint /models/model_base \
  --output /output/game.delta_q.jsonl \
  --source-version 1
```

### Consume them in training

```yaml
exit_sidecar_path: /output/exit_index.jsonl
delta_q_sidecar_path: /output/delta_q_index.jsonl
```

## Reports

Both builders also emit a JSON report next to the JSONL output. The report path is derived from the output path using a `.report.json` sibling artifact.

Use that report to inspect:

- how many labels were emitted
- any validation/coverage summaries specific to that lane

## When to use ExIt vs DeltaQ

Use ExIt sidecars when:

- you want replay-indexed search-derived root/visit-style supervision
- you are working on the shipped baseline ExIt carrier

Use DeltaQ sidecars when:

- you are evaluating or training the narrow DeltaQ lane
- you are prepared to keep provenance and version contracts tighter
- you understand that the lane is implemented but not default-on

## Common failure modes

- Wrong `source_version` means join-time hydration will fail.
- Wrong checkpoint identity means `source_net_hash` will not match.
- Legal-mask drift prevents hydration even when the replay looks similar.
- DeltaQ sidecars reject records that violate the discard-only mask contract.
- A valid JSONL file is not enough; semantics/provenance must also match.
